# JMLC 2026 — evidence bundle

Всё, на что ссылается защита, лежит здесь. Каждое число в таблицах ниже взято из
`aggregates/matrix_table.json`, который целиком выводится из сырых RunRecord в
`fair/runs/` — никакая метрика не пересчитывается вручную и не переписывается
между документами.

Ссылки вида `DEC-013` указывают на журнал решений
[docs/DECISIONS.md](../../docs/DECISIONS.md); протокол целиком —
[docs/PROJECT_CONTRACT.md](../../docs/PROJECT_CONTRACT.md).

Проверка бандла:

```bash
poetry run python scripts/validate_evidence.py reports/jmlc_2026
```

Валидатор перепроверяет заявленное, а не доверяет ему: статусы всех cells,
совпадение config hash с frozen/resolved spec, единый пиннованный digest
датасета, общий evaluation context на каждом горизонте, объявленные seeds,
равный HPO-бюджет у reservoir-моделей, конечность headline-метрик и то, что
ресурсный профиль измерен на том же config hash, что и опубликованный
результат. Отредактированная руками таблица валидацию не проходит.

## Состав

| Путь | Что это |
|---|---|
| `dataset_manifest.json` | Пиннованный источник данных: URL, лицензия, SHA-256 архива и сырого файла. |
| `fair/runs/*.json` | Сырые RunRecord всех 14 cells: frozen + resolved spec, метрики, selection, evaluation context, версии библиотек, git hash. |
| `fair/artifacts/*.npz` | Предсказания и test-таргеты по одной ячейке на cell (для reservoir — первый seed). |
| `fair/summary.json` | Компактная сводка прогона матрицы со временем выполнения каждой cell. |
| `aggregates/matrix_table.{json,csv}` | Опубликованная таблица — единственный источник чисел для README, слайдов и графиков. |
| `aggregates/eda_summary.json`, `eda_report.md`, `plots/eda_*.png` | EDA: покрытие, пропуски, распределения, ACF, суточный и недельный профиль, сравнение split. |
| `hardware_profile.json` | Обезличенный профиль машины и протокол измерений (DEC-008). |
| `profiles/` | Ресурсный профиль по cells: latency p50/p95, throughput, peak RSS, размер модели и рабочего состояния. |

Smoke-прогон (`reports/jmlc_2026/smoke/`) намеренно не версионируется: это
артефакт гейта, который `verify.sh smoke` пересоздаёт, а каждый прогон пишет
новые timestamps. Публикуемые числа — это fair-матрица.

## Протокол

Данные: UCI Individual Household Electric Power Consumption, почасовой ряд,
окно 12 000 часов, split 0.6 / 0.2 / 0.2 по времени без перемешивания.
Препроцессинг каузальный, scaler обучается только на train.

Оценка (DEC-012 / DEC-013): режим `fixed_horizon` для обоих горизонтов, включая
h=1 — `one_step` на несдвинутом ряде UCI запрещён как target leakage. Общий
per-split washout 200 часов, поэтому оцениваемые target-индексы для горизонта
`h` начинаются с `200 + h`. Все семь моделей на данном горизонте оцениваются на
одном и том же наборе наблюдаемых target-таймстемпов; это проверяется по
записанному в каждый RunRecord `EvaluationContext` (DEC-018), а не постфактум.

Селекция: reservoir-модели получают равный бюджет 20 Optuna-trials по
validation NRMSE_std, затем лучшая конфигурация оценивается на 5 seeds
(приводится среднее ± SD по seeds). Ridge AR(24) выбирает alpha по фиксированной
сетке на validation, persistence и seasonal persistence детерминированы и
запускаются один раз (DEC-014/DEC-015). Test не участвует в селекции ни у одного
семейства.

Метрики: NRMSE_std — headline; MASE считается по train-only seasonal scale с
лагом 24; MAE skill — относительно seasonal persistence на том же test target
set. Отрицательный skill означает, что модель хуже сезонного наивного прогноза.

## Как читать эти числа

**ESN — лучшая модель на обоих горизонтах**, но выигрыш у сильного baseline
небольшой: 0.6647 против 0.6760 у Ridge AR на h=1 (1.7 %) и 0.8705 против
0.9023 на h=24 (3.5 %). Разброс по seeds (±0.002 и ±0.005) заметно меньше этого
разрыва, то есть порядок ESN → Ridge AR устойчив, но заявлять кратное
превосходство reservoir-моделей эти данные не позволяют.

**LSM хуже сезонного наива на h=24** (MAE skill −0.019, MASE 1.05). Это
публикуется как есть: конфигурация LSM в рамках равного бюджета в 20 trials не
решает задачу, и заменять этот результат более удачным подбором было бы
подгонкой.

**На h=24 persistence и seasonal persistence совпадают до последнего знака.**
Это не ошибка: при горизонте 24 и сезонном периоде 24 обе модели читают одно и
то же значение `values[tau - 24]`. По той же причине MAE skill seasonal
persistence равен ровно нулю на обоих горизонтах — модель сравнивается сама с
собой; ноль здесь работает как проверка корректности скоринга.

**Качество деградирует с горизонтом у всех семи моделей**, и разрыв между
лучшей моделью и сезонным наивом сжимается с 0.40 до 0.15 по MAE skill —
суточный горизонт на этом ряде существенно труднее часового.

## Ресурсный профиль

Профилирование — отдельный проход (`scripts/run_profiling.py`), никогда не совмещённый с
обучением: обучение выполняется вне таймируемого участка, внутри измеряется ровно один шаг
вывода. Протокол: ≥100 warmup-шагов, ≥1000 измеряемых шагов, `perf_counter_ns`,
однопоточный режим; сырые по-шаговые измерения сохранены в `profiles/*.json`.

| Модель | p50, h=1 | p95, h=1 | p50, h=24 | Рабочее состояние, h=1 | Размер модели |
|---|---|---|---|---|---|
| persistence | 0.27 мкс | 0.29 мкс | 0.39 мкс | 8 Б | 135 Б |
| seasonal_persistence | 0.40 мкс | 0.42 мкс | 0.40 мкс | 192 Б | 319 Б |
| ridge_ar | 3.37 мкс | 3.47 мкс | 3.56 мкс | 192 Б | 1.5 КиБ |
| logistic | 9.59 мкс | 9.93 мкс | 10.91 мкс | 3.9 КиБ | 20.4 КиБ |
| esn | 21.82 мкс | 27.58 мкс | 17.94 мкс | 2.3 КиБ | 75.0 КиБ |
| leaky_esn | 22.09 мкс | 29.71 мкс | 22.01 мкс | 2.3 КиБ | 711.0 КиБ |
| lsm | 43.05 мкс | 58.44 мкс | 39.97 мкс | 3.1 КиБ | 1265.1 КиБ |

### Почему в артефактах два измерения latency

Каждая ячейка содержит `latency` и `latency_deployable`. Первое — стоимость шага **как
он реализован в этой библиотеке**, через `sklearn.predict`/`StandardScaler.transform`.
Второе — та же модель и те же коэффициенты, но readout вычисляется арифметически
(`coef @ h + intercept`). Предсказания обоих путей совпадают с точностью до
`rtol=1e-9` (проверяется тестом).

Разница не косметическая: per-call валидация входа в sklearn стоит 32–42 мкс независимо
от размера модели и составляла **55–96 %** измеренного времени. В as-implemented виде
Ridge AR (87.4 мкс) выглядел бы медленнее ESN (73.1 мкс) — при том, что в deployable-виде
он в 6.5 раза **быстрее** (3.37 против 21.82 мкс). Публиковать первое как сравнение
моделей значило бы ранжировать их по числу вызовов фреймворка, поэтому в таблицах и на
Pareto-графиках используется deployable-измерение, а as-implemented остаётся в артефактах
как честная характеристика текущей реализации.

### Память

`peak_rss_bytes` измеряется в отдельном процессе, но этот процесс порождён через `fork`,
поэтому наследует резидентную память родителя (интерпретатор, numpy/sklearn/reservoirpy,
загруженный датасет) — 87–244 МБ во всех ячейках. Это footprint процесса, а не модели, и
`peak_rss_delta_bytes` относительно родителя для лёгких моделей уходит в минус. Поэтому
на Pareto-графике по памяти используется `working_state_bytes` — размер рабочего состояния,
которое действительно нужно держать между шагами; вместе с `serialized_model_bytes` это и
есть edge-релевантные числа. Peak RSS приводится как верхняя граница footprint процесса.

### Что из этого следует для edge

Резервуар покупает точность ценой ресурсов. На h=1 ESN даёт 1.7 % выигрыша по NRMSE_std
над Ridge AR, но стоит в 6.5 раза больше времени на шаг (21.82 против 3.37 мкс), в 12 раз
больше рабочего состояния (2.3 КиБ против 192 Б) и в 50 раз больше памяти под саму модель
(75.0 КиБ против 1.5 КиБ). На h=24 соотношение похожее: 3.5 % точности за примерно
пятикратную стоимость шага.

Pareto-фронт по latency на обоих горизонтах один и тот же: persistence (самый дешёвый) →
Ridge AR (практически вся точность за малую долю стоимости) → ESN (лучшая точность). По
памяти фронт тот же, за одним исключением: на h=24 seasonal persistence делит фронт с
persistence, потому что при `h = season = 24` это буквально один и тот же предиктор с тем
же размером состояния. Остальные модели — leaky ESN, logistic, LSM — доминируются: они
одновременно дороже и хуже. Для
edge-сценария на этом ряде это означает, что резервуар оправдан только там, где 1.7–3.5 %
NRMSE стоят пятикратной стоимости вывода.

## Воспроизведение

```bash
# 1. Данные (сверяются с dataset_manifest.json по SHA-256; в Git не попадают)
poetry run python scripts/download_jmlc_data.py

# 2. Fair-матрица: 14 cells, 20 trials, 5 seeds
poetry run python scripts/run_jmlc_matrix.py \
    --config configs/jmlc/fair.yaml --output reports/jmlc_2026/fair

# 3. Ресурсный профиль и hardware profile
poetry run python scripts/run_profiling.py \
    --config configs/jmlc/fair.yaml \
    --runs reports/jmlc_2026/fair/runs \
    --output reports/jmlc_2026/profiles \
    --hardware-output reports/jmlc_2026/hardware_profile.json

# 4. Пересборка агрегатов и проверка бандла
poetry run python scripts/validate_evidence.py reports/jmlc_2026 --write
```

`run_matrix` перед стартом хеширует сырой файл и отказывается считать матрицу,
если он не совпадает с `raw_sha256` из конфига (DEC-017), поэтому числа выше
привязаны к конкретным байтам, а не к имени файла.

## Ограничения

- Один датасет и одна машина: результаты не переносятся на другое оборудование
  или другой ряд без повторного прогона.
- Аппаратного счётчика энергии нет, поэтому energy во всех записях помечен
  `unavailable`; прокси-метрики вместо измерений не публикуются (DEC-008).
- Reservoir-модели сравниваются при равном бюджете в 20 trials; больший бюджет
  мог бы изменить порядок внутри reservoir-семейства.
- Latency измерена на CPU одной машины вне обучения; её следует читать как порядок
  величины, а не как гарантию для конкретного edge-устройства. Deployable-измерение
  снимает накладной расход sklearn, но остаётся Python-реализацией: нативная реализация
  тех же вычислений была бы быстрее, вероятно неодинаково для разных семейств.
- Peak RSS измерен в forked-процессе и включает резидентную память родителя, поэтому
  характеризует footprint процесса, а не модели (см. «Ресурсный профиль»).
