# JMLC 2026 — evidence bundle

Всё, на что ссылается защита, лежит здесь. Каждое число в таблицах ниже взято из
`aggregates/matrix_table.json`, который целиком выводится из сырых RunRecord в
`fair/runs/` — никакая метрика не пересчитывается вручную и не переписывается
между документами.

Ссылки вида `DEC-013` указывают на журнал решений
[docs/DECISIONS.md](../../docs/DECISIONS.md); протокол целиком —
[docs/PROJECT_CONTRACT.md](../../docs/PROJECT_CONTRACT.md).

Проверка бандла:

```bash
poetry run python scripts/validate_evidence.py reports/jmlc_2026
```

Валидатор перепроверяет заявленное, а не доверяет ему: статусы всех cells,
совпадение config hash с frozen/resolved spec, единый пиннованный digest
датасета, общий evaluation context на каждом горизонте, объявленные seeds,
равный HPO-бюджет у reservoir-моделей, конечность headline-метрик и то, что
ресурсный профиль измерен на том же config hash, что и опубликованный
результат. Отредактированная руками таблица валидацию не проходит.

## Протокол

Данные: UCI Individual Household Electric Power Consumption, почасовой ряд,
окно 12 000 часов, split 0.6 / 0.2 / 0.2 по времени без перемешивания.
Препроцессинг каузальный, scaler обучается только на train.

Оценка (DEC-012 / DEC-013): режим `fixed_horizon` для обоих горизонтов, включая
h=1 — `one_step` на несдвинутом ряде UCI запрещён как target leakage. Общий
per-split washout 200 часов, поэтому оцениваемые target-индексы для горизонта
`h` начинаются с `200 + h`. Все семь моделей на данном горизонте оцениваются на
одном и том же наборе наблюдаемых target-таймстемпов; это проверяется по
записанному в каждый RunRecord `EvaluationContext` (DEC-018), а не постфактум.

Селекция: reservoir-модели получают равный бюджет 20 Optuna-trials по
validation NRMSE_std, затем лучшая конфигурация оценивается на 5 seeds
(приводится среднее ± SD по seeds). Ridge AR(24) выбирает alpha по фиксированной
сетке на validation, persistence и seasonal persistence детерминированы и
запускаются один раз (DEC-014/DEC-015). Test не участвует в селекции ни у одного
семейства.

Метрики: NRMSE_std — headline; MASE считается по train-only seasonal scale с
лагом 24; MAE skill — относительно seasonal persistence на том же test target
set. Отрицательный skill означает, что модель хуже сезонного наивного прогноза.

## Как читать эти числа

**ESN — лучшая модель на обоих горизонтах**, но выигрыш у сильного baseline
небольшой: 0.6647 против 0.6760 у Ridge AR на h=1 (1.7 %) и 0.8705 против
0.9023 на h=24 (3.5 %). Разброс по seeds (±0.002 и ±0.005) заметно меньше этого
разрыва, то есть порядок ESN → Ridge AR устойчив, но заявлять кратное
превосходство reservoir-моделей эти данные не позволяют.

**LSM хуже сезонного наива на h=24** (MAE skill −0.019, MASE 1.05). Это
публикуется как есть: конфигурация LSM в рамках равного бюджета в 20 trials не
решает задачу, и заменять этот результат более удачным подбором было бы
подгонкой.

**На h=24 persistence и seasonal persistence совпадают до последнего знака.**
Это не ошибка: при горизонте 24 и сезонном периоде 24 обе модели читают одно и
то же значение `values[tau - 24]`. По той же причине MAE skill seasonal
persistence равен ровно нулю на обоих горизонтах — модель сравнивается сама с
собой; ноль здесь работает как проверка корректности скоринга.

**Качество деградирует с горизонтом у всех семи моделей**, и разрыв между
лучшей моделью и сезонным наивом сжимается с 0.40 до 0.15 по MAE skill —
суточный горизонт на этом ряде существенно труднее часового.

Профилирование — отдельный проход (`scripts/run_profiling.py`), никогда не совмещённый с
обучением: обучение выполняется вне таймируемого участка, внутри измеряется ровно один шаг
вывода. Протокол: ≥100 warmup-шагов, ≥1000 измеряемых шагов, `perf_counter_ns`,
однопоточный режим; сырые по-шаговые измерения сохранены в `profiles/*.json`.

| esn | 21.82 мкс | 27.58 мкс | 17.94 мкс | 2.3 КиБ | 75.0 КиБ |

### Почему в артефактах два измерения latency

Каждая ячейка содержит `latency` и `latency_deployable`. Первое — стоимость шага **как
он реализован в этой библиотеке**, через `sklearn.predict`/`StandardScaler.transform`.
Второе — та же модель и те же коэффициенты, но readout вычисляется арифметически
(`coef @ h + intercept`). Предсказания обоих путей совпадают с точностью до
`rtol=1e-9` (проверяется тестом).

Разница не косметическая: per-call валидация входа в sklearn стоит 32–42 мкс независимо
от размера модели и составляла **55–96 %** измеренного времени. В as-implemented виде
Ridge AR (87.4 мкс) выглядел бы медленнее ESN (73.1 мкс) — при том, что в deployable-виде
он в 6.5 раза **быстрее** (3.37 против 21.82 мкс). Публиковать первое как сравнение
моделей значило бы ранжировать их по числу вызовов фреймворка, поэтому в таблицах и на
Pareto-графиках используется deployable-измерение, а as-implemented остаётся в артефактах
как честная характеристика текущей реализации.

### Память

`peak_rss_bytes` измеряется в отдельном процессе, но этот процесс порождён через `fork`,
поэтому наследует резидентную память родителя (интерпретатор, numpy/sklearn/reservoirpy,
загруженный датасет) — 87–244 МБ во всех ячейках. Это footprint процесса, а не модели, и
`peak_rss_delta_bytes` относительно родителя для лёгких моделей уходит в минус. Поэтому
на Pareto-графике по памяти используется `working_state_bytes` — размер рабочего состояния,
которое действительно нужно держать между шагами; вместе с `serialized_model_bytes` это и
есть edge-релевантные числа. Peak RSS приводится как верхняя граница footprint процесса.

### Что из этого следует для edge

Резервуар покупает точность ценой ресурсов. На h=1 ESN даёт 1.7 % выигрыша по NRMSE_std
над Ridge AR, но стоит в 5.7 раза больше времени на шаг (21.39 против 3.75 мкс), в 12 раз
больше рабочего состояния (2.3 КиБ против 192 Б), в 50 раз больше памяти под саму модель
(75.0 КиБ против 1.5 КиБ) и в 5.3 раза больше энергии на вывод (0.1297 против 0.0245 мДж).
На h=24 соотношение похожее: 3.5 % точности за примерно пятикратную стоимость шага.

Pareto-фронт по latency на обоих горизонтах один и тот же: persistence (самый дешёвый) →
Ridge AR (практически вся точность за малую долю стоимости) → ESN (лучшая точность). Фронт
по энергии совпадает с фронтом по latency — на одной машине стоимость шага почти целиком
определяется временем под нагрузкой. По памяти фронт тот же, за одним исключением: на h=24 seasonal persistence делит фронт с
persistence, потому что при `h = season = 24` это буквально один и тот же предиктор с тем
же размером состояния. Остальные модели — leaky ESN, logistic, LSM — доминируются: они
одновременно дороже и хуже. Для
edge-сценария на этом ряде это означает, что резервуар оправдан только там, где 1.7–3.5 %
NRMSE стоят пятикратной стоимости вывода.

## Энергия

Источник — powercap-интерфейс ядра, `/sys/class/powercap/intel-rapl:*`. Берутся
домены верхнего уровня (`package-0`), а не их поддомены: иначе одна и та же
энергия сложилась бы дважды. Переполнение счётчика обрабатывается по
`max_energy_range_uj`.

Протокол одного измерения:

1. Окно простоя длительностью `energy_window_s` (2 с) — базовая линия
   статического потребления процессора.
2. Окно под нагрузкой той же целевой длительности: `step_fn` вызывается не
   менее 1000 раз и не менее 2 с. Начальное число шагов оценивается по уже
   измеренной медианной задержке, но эта оценка из другого прохода и может
   ошибаться, поэтому фактическая длительность проверяется после прогона и при
   нехватке окно расширяется по наблюдённой стоимости шага. Итог помечается
   `window_target_met`.
3. Публикуются обе величины: полная (`total_energy_j`) и net — за вычетом
   простоя, линейно приведённого к длительности окна.

**Чем это не является.** RAPL меряет пакет процессора целиком, вместе со всем,
что на нём в этот момент исполняется. Даже net-величина — это разность двух
измерений всей машины, а не потребление резервуара. Читать её следует как
порядок величины и как основание для сравнения моделей между собой на одной
машине, а не как энергопотребление модели на произвольном устройстве.

Если счётчик недоступен (нет домена, файл закрыт для пользователя — с
CVE-2020-8694 он root-only) или окно короче периода обновления счётчика, в
записи стоит `status: "unavailable"` с причиной. Ноль там не появляется
никогда: нуль, записанный как измеренная энергия, выглядит числом и при этом
утверждает, что модель ничего не потребляет.

Измерено на этой матрице (h=1, net, мДж на один вывод):

| Модель | p50 шага | Энергия | Рабочее состояние |
|---|---|---|---|
| persistence | 0.31 мкс | 0.00096 | 8 Б |
| ridge_ar | 3.75 мкс | 0.02449 | 192 Б |
| logistic | 14.00 мкс | 0.07566 | 4000 Б |
| esn | 21.39 мкс | 0.12974 | 2400 Б |
| leaky_esn | 25.53 мкс | 0.14605 | 2400 Б |
| lsm | 51.90 мкс | 0.40088 | 3200 Б |

Энергия монотонна по задержке шага — ожидаемо для одной машины, где стоимость
шага почти целиком определяется временем, которое процессор проводит под
нагрузкой.

## Прокси активности

Блок `activity` в каждом профиле несёт три вещи: аналитический счёт операций
на шаг (`operations`), разреженность рабочего состояния (`state_sparsity`) и
спайковую статистику (`spiking`, не `null` только у LSM).

**Прокси никогда не пересчитываются в джоули.** Для такого пересчёта нужна
модель энергопотребления железа — сколько джоулей стоит один MAC на этом
конкретном процессоре, — которой у проекта нет. Число, полученное умножением
MAC на выдуманный коэффициент, читалось бы как измерение, ничем таковым не
являясь. Поэтому `activity` и `energy` — разные блоки, и связи между ними в
артефактах нет.

Счёт операций аналитический: он выводится из форм матриц и из того, что
делает `step()`, а не измеряется. Конвенция — один MAC на скалярно-векторное
умножение (по одному на юнит) и один на ненулевой вес матрицы; сложения без
множителя не считаются, нелинейности считаются отдельно.

Счёт реализован у шести архитектур из семи. Исключение — `fhn`: её шаг это
RK4-интегрирование, где работу определяет поэлементная арифметика схемы, а не
матвек, и результат рос бы с `internal_steps` — параметром численной схемы, а
не ёмкости модели. Под конвенцию выше это не ложится, поэтому профиль пишет
`backend: "unavailable"` вместо числа, несопоставимого с остальными. `deep_esn`
и `qrc` счёт отдают, но в этой таблице их нет по другой причине: они не входят
в real-data матрицу (`docs/PROJECT_CONTRACT.md`), а профилируются только её
ячейки.

Для LSM дополнительно публикуются `spikes_per_step` и
`synaptic_events_per_step`: второе учитывает исходящую связность каждого
спайкнувшего нейрона и потому отличается от первого. Для не-спайковых
резервуаров оба поля — `null`, а не ноль: ноль читался бы как «прогнали и не
спайкнуло», что неверно для tanh-резервуара, который не спайкует в принципе.

## Fair против best-effort

Fair-контур даёт всем reservoir-моделям одинаковый бюджет настройки (20
trials, DEC-004) — только так сравнение измеряет архитектуру, а не то, кому
досталось больше вычислений. Best-effort отвечает на другой вопрос: чего
модель достигает, если настраивать её столько, сколько она просит (ESN,
leaky ESN, logistic — 60 trials; LSM — 40).

Тройной бюджет покупает немного, но меняет порядок:

| Модель | h | fair | best-effort | выигрыш |
|---|---|---|---|---|
| esn | 1 | 0.6647 | 0.6647 | 0.00 % |
| leaky_esn | 1 | 0.6743 | **0.6607** | 2.02 % |
| logistic | 1 | 0.7513 | 0.7487 | 0.34 % |
| lsm | 1 | 0.9449 | 0.9422 | 0.29 % |
| esn | 24 | 0.8705 | 0.8696 | 0.11 % |
| leaky_esn | 24 | 0.8910 | **0.8674** | 2.66 % |
| logistic | 24 | 0.9656 | 0.9379 | 2.86 % |
| lsm | 24 | 0.9832 | 0.9731 | 1.03 % |

Baseline не настраиваются и потому идентичны в обоих контурах — это проверка
на месте: разойдись они, что-то поехало бы в самом протоколе.

Содержательный вывод один и его стоит назвать прямо: **лучшая reservoir-модель
меняется**. В fair на обоих горизонтах выигрывает ESN, в best-effort — leaky
ESN, причём именно потому, что leaky ESN выигрывает от дополнительного бюджета
больше всех (у него на один настраиваемый параметр больше). То есть вывод
«ESN лучше leaky ESN» — это утверждение о поведении при 20 trials, а не о
превосходстве архитектуры.

Что при этом **не** меняется: обе reservoir-модели по-прежнему обходят Ridge AR
(0.6760 на h=1) — на 1.7 % в fair и на 2.3 % в best-effort, — и разрыв не
приближается к тому, чтобы оправдать пятикратную стоимость шага. Общий вывод
для edge из раздела выше остаётся в силе в обоих контурах.

Профили ресурсов сняты только с fair-матрицы. Best-effort меняет
гиперпараметры, а с ними и стоимость шага, поэтому переиспользовать под него
fair-профиль было бы подлогом; отдельного профиля второго контура в бандле
нет, и стоимостных осей для него не публикуется.

## Воспроизведение

```bash
# 1. Данные (сверяются с dataset_manifest.json по SHA-256; в Git не попадают)
poetry run python scripts/download_jmlc_data.py

# 2. Fair-матрица: 14 cells, 20 trials, 5 seeds
poetry run python scripts/run_jmlc_matrix.py \
    --config configs/jmlc/fair.yaml --output reports/jmlc_2026/fair

# 3. Ресурсный профиль и hardware profile
poetry run python scripts/run_profiling.py \
    --config configs/jmlc/fair.yaml \
    --runs reports/jmlc_2026/fair/runs \
    --output reports/jmlc_2026/profiles \
    --hardware-output reports/jmlc_2026/hardware_profile.json

# 4. Best-effort матрица (индивидуальные бюджеты настройки)
poetry run python scripts/run_jmlc_matrix.py \
    --config configs/jmlc/best_effort.yaml --output reports/jmlc_2026/best_effort

# 5. Пересборка агрегатов и проверка обоих контуров
poetry run python scripts/validate_evidence.py reports/jmlc_2026 \
    --modes fair,best_effort --write

# 6. Диаграммы и отчёт выбора
poetry run python scripts/plot_pareto.py \
    --bundle reports/jmlc_2026 --output reports/jmlc_2026/plots
poetry run rcbench select --bundle reports/jmlc_2026 --horizon 1 \
    --max-latency-us 25 --max-state-bytes 4096 \
    --output reports/jmlc_2026/selection.md
```

Профилирование читает RAPL-счётчик. Если он недоступен, шаг 3 отработает без
ошибки, но блок `energy` во всех ячейках будет `unavailable`, а
`plot_pareto.py` пропустит третью диаграмму с названной причиной — это
штатный исход, а не отказ.

`run_matrix` перед стартом хеширует сырой файл и отказывается считать матрицу,
если он не совпадает с `raw_sha256` из конфига (DEC-017), поэтому числа выше
привязаны к конкретным байтам, а не к имени файла.

## Ограничения

- Один датасет и одна машина: результаты не переносятся на другое оборудование
  или другой ряд без повторного прогона.
- Энергия измерена по package-домену процессора целиком, а не по модели: это
  верхняя граница с вычтенным простоем, а не изолированное потребление
  резервуара. См. «Энергия» ниже.
- Reservoir-модели в fair-контуре сравниваются при равном бюджете в 20 trials.
  Второй контур показывает, что больший бюджет действительно меняет порядок
  внутри reservoir-семейства — см. «Fair против best-effort».
- Latency измерена на CPU одной машины вне обучения; её следует читать как порядок
  величины, а не как гарантию для конкретного edge-устройства. Deployable-измерение
  снимает накладной расход sklearn, но остаётся Python-реализацией: нативная реализация
  тех же вычислений была бы быстрее, вероятно неодинаково для разных семейств.
- Peak RSS измерен в forked-процессе и включает резидентную память родителя, поэтому
  характеризует footprint процесса, а не модели (см. «Ресурсный профиль»).
