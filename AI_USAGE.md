# Использование ИИ в RC-Bench

Статус документа: рабочее раскрытие использования ИИ. Срез репозитория,
проверенный при подготовке: `dev` на коммите `39c6f5b`. Документ описывает
процесс разработки, а не подтверждает научные результаты.

## Назначение

ИИ-агенты использовались для анализа репозитория, подготовки локальных
изменений, тестов и документации по утверждённому плану JMLC. Они не определяли
научную цель самостоятельно и не имеют права публиковать результат без
проверяемых артефактов.

Этот файл нужен для прозрачности:

- какие решения оставались за человеком;
- как разделялась работа основного и task-агентов;
- какие ограничения применялись к изменениям;
- как предложения ИИ проверялись перед интеграцией;
- какие утверждения пока не подтверждены.

## Ответственность человека

Пользователь предоставил и утвердил контракт, обязательный объём и порядок
работы. Он отдельно разрешил операции с рабочими ветками, изолированные
worktree и вычислительную нагрузку для будущих экспериментов.

За человеком сохраняются:

- утверждение и изменение научной постановки, датасета и fair-протокола;
- принятие решений, выходящих за рамки
  [PROJECT_CONTRACT.md](docs/PROJECT_CONTRACT.md);
- финальная научная интерпретация метрик, графиков и ограничений;
- проверка материалов защиты;
- окончательное разрешение на слияние итогового PR `dev → main`.

Этот документ не приписывает человеку или ИИ неподтверждённое ручное авторство
конкретных строк кода. Git фиксирует изменения и их интеграцию, но сам по себе
не доказывает способ создания каждой строки.

## Роли ИИ и выполненные задачи

Роли задаются
`docs/agent/AGENT_WORKFLOW.md` (процессные документы ведутся в ветке `dev`). Они описывают область
ответственности, а не постоянных персонажей или конкретную модель ИИ.

### Основной агент

Основной агент координирует зависимости backlog, владеет контрактом,
интеграцией и cross-cutting изменениями. К ним относятся общие схемы,
`ExperimentSpec`, `ResultSpec`, RunRecord, pipeline, evidence bundle и
release gate.

На проверенном срезе основной агент:

- установил repository-native harness;
- интегрировал task-ветки последовательно в `dev`;
- сохранил под своей ответственностью cross-cutting задачи `COR-002` и
  `ENERGY-001`;
- проверял diff и acceptance-команды каждой интегрированной кодовой задачи;
- после каждой интеграции повторно запускал quick gate;
- обновлял статусы backlog и устойчивые решения отдельно от task-веток.

`bb38f1a` и текущим

| Architecture & Quality | `COR-003` | Predictions для demo сделаны явными и ограниченными; `140798e` |

## Контроль работы агентов

Каждая делегированная задача задавалась карточкой с:

- task ID, целью и base commit;
- разрешёнными и запрещёнными путями;
- обязательными материалами для чтения;
- acceptance checks и ожидаемыми артефактами;
- условиями остановки.

Для изменений применялись следующие ограничения:

1. Один task ID выполнялся в короткоживущей ветке `codex/<task-id>-<slug>` и
   отдельном worktree.
2. Параллельные агенты не получали пересекающиеся области записи.
3. Task-агенты не выполняли push, merge в `dev` или изменения `main`.
4. Для изменений кода сначала воспроизводился дефект или добавлялся тест,
   затем вносилась минимальная реализация.
5. Перед handoff проверялись acceptance-команды, `git diff --check`, состав
   diff и чистота рабочей ветки.
6. Handoff включал base/final SHA, изменённые файлы, фактические результаты
   команд, ограничения и непроверенные предположения.
7. Основной агент отдельно просматривал diff, сопоставлял его с task scope,
   повторял проверки и только затем интегрировал изменения.

## Проверки и известные ограничения

Минимальная локальная проверка задаётся командой:

```bash
bash scripts/verify.sh quick
```

На текущем срезе она запускает unit-тесты без integration marker, проверяет CLI
`list-datasets` и `list-reservoirs`, затем выполняет `git diff --check`.
PostgreSQL и Redis не требуются для unit gate; API integration test остаётся
отдельно помеченным и требует внешние сервисы.

Важно:

- наличие GitHub Actions workflow подтверждено кодом, но успешный удалённый
  Actions run в этом документе не заявляется;
- smoke и release gates не заявляются пройденными;
- `DATA-002` и зависящие от него real-data задачи на этом срезе не завершены;
- smoke/full экспериментальная матрица, evidence bundle и итоговые графики ещё
  не подтверждены;
- этот файл не содержит экспериментальных чисел, оценок экономии времени или
  заявлений о производительности моделей;
- аппаратное измерение энергии недоступно по утверждённому контракту и не
  заменяется TDP, CPU time или паспортной мощностью;
- имена и версии использованных моделей ИИ здесь не указываются, поскольку
  проверяемая запись для такого утверждения не предоставлена.

## Воспроизводимость и traceability

Связь изменения с процессом восстанавливается через:

- task ID в backlog и имени рабочей ветки;
- base/final SHA из handoff;
- интегрированный commit SHA в `dev`;
- тест, acceptance-команды и verification gate;
- записи в
  [DECISIONS.md](docs/DECISIONS.md) для устойчивых решений.

Историю описанного среза можно проверить командой:

```bash
git log --oneline bb38f1a..39c6f5b
```

Для будущих научных результатов этого недостаточно. Каждая итоговая точка
должна дополнительно ссылаться на commit SHA, frozen и resolved spec, seed,
dataset manifest с checksum, версии зависимостей и hardware profile. Эти
требования описаны в project contract; их наличие должно проверяться по
evidence bundle, а не по текстовому заявлению.

## Сессия 26 июля 2026 — приведение репозитория в соответствие с описанием проекта

Отдельная сессия по плану
[`docs/agent/plans/2026-07-25-pdf-conformance.md`](docs/agent/plans/2026-07-25-pdf-conformance.md),
составленному после сверки репозитория с текстом описания проекта. План
зафиксировал 14 подтверждённых заявлений и 11 расхождений, разложенных на 13
задач.

### Что делал основной агент

Задачи, затрагивающие сквозные файлы (`core/schema.py`, `runners/`,
`reporting/`, `BACKLOG.md`, `DECISIONS.md`), а также всё, где нужно было
принимать решение о протоколе: MODE-001, MODE-002, PROF-004, ENERGY-003,
SELECT-001, API-001, EXP-004, DOC-003. Реализация велась по TDD — тест,
падение, реализация, гейт.

### Что делали сабагенты

- **Реализация** (по одной задаче на агента, последовательно, в основном
  дереве): PROXY-001 (счёт операций и разреженность), ENERGY-002 (backend
  Intel RAPL).
- **Ревью** (отдельные агенты, каждому — диапазон коммитов и раздел плана):
  проверка ENERGY-002, MODE-002, PROF-004 и сводное ревью ENERGY-003 вместе с
  раундами правок.

Ревью потребовали от агента не только прочитать diff, но и проверить
дискриминирующую силу тестов мутациями: сломать инвариант в рабочей копии,
убедиться, что тест краснеет, и откатить. Это дало содержательные находки, а
не пересказ diff.

### Что ревью нашло и что было исправлено

Три Important-находки, каждая с воспроизведением, все закрыты отдельными
коммитами:

1. Окно измерения короче периода обновления RAPL-счётчика публиковало ноль как
   измеренную энергию с `window_target_met: true`. Теперь такой случай —
   явный `unavailable` с причиной; профиль дополнительно прогоняет свой блок
   через `EnergyResult` перед записью (коммит `16f8c27`).
2. Правило равного бюджета (DEC-004) обходилось reservoir-ячейкой с
   `use_hpo=False`: матрица с ESN на 100 trial'ах и LSM на стоковых
   гиперпараметрах прошла бы гейт как равное сравнение (`16f8c27`).
3. Режим протокола, объявленный записями, не сверялся с каталогом, под именем
   которого они лежат, — best-effort-ячейки, попавшие в `fair/runs`,
   проходили гейт зелёными (`08b2c34`).

### Что проверено человеком и машиной, а не заявлено агентом

| Что | Как проверено |
|---|---|
| Доступ к RAPL и реальные значения счётчика | Человек открыл доступ; агент прочитал `energy_uj` напрямую, без обёрток |
| Энергия во всех 14 ячейках | Проход профилирования на этой машине; соотношения между моделями сверены с задержкой и MAC |
| Неизменность `config_hash` после добавления `ProtocolSpec.mode` | `git diff` по `fair/runs/` — ни одного вхождения `config_hash` |
| Сервисный контур целиком | Человек установил Docker; `docker compose up -d --build`, `curl localhost/`, логи worker, затем `down` |
| Integration-тесты владельца и baseline-спек | `poetry run pytest -m integration` против настоящих PostgreSQL и Redis — 5 passed |
| Полный релизный гейт | `bash scripts/verify.sh release` |

Все числа в README, README бандла и `selection.md` получены прогоном и
скопированы из артефактов, а не написаны по памяти.

### Признанное ограничение сессии

Профиль на edge-устройстве (Jetson) не снят — устройства нет. В README он
стоит в разделе «Запланировано», а не описывается как возможность платформы.

## Проверка AI-assisted изменений

Выводы агентов рассматривались как предложения, а не как доказательство
корректности. Интегрированные AI-assisted изменения проходили просмотр diff,
ограничение scope, автоматические тесты и повторный quick gate основным
агентом. Обнаруженные ошибки исправлялись отдельным проверяемым изменением.

Такой процесс снижает риск, но не исключает дефекты и не заменяет научную
экспертизу. Финальная интерпретация результатов, выбор утверждений для защиты и
решение о слиянии остаются под контролем человека.
