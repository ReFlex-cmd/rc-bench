# RC-Bench Agent Guide

Этот файл задаёт обязательные правила для Codex и любых сабагентов, работающих с `rc-bench` перед защитой JMLC 27 июля 2026 года.

## Перед началом любой задачи

1. Прочитай `docs/agent/PROJECT_CONTRACT.md`, `docs/agent/BACKLOG.md`, `docs/agent/DECISIONS.md` и карточку текущей задачи.
2. Выполни `git status --short --branch`, `git log -5 --oneline` и проверь, что работа ведётся от актуальной ветки `dev`.
3. Не начинай реализацию, если рабочее дерево содержит неизвестные изменения, задача не имеет критерия готовности или требует изменить зафиксированный контракт.
4. Выбери ровно одну задачу из backlog. Не расширяй её скрыто.

## Ветки и интеграция

- Рабочая база — `dev`. Прямые коммиты и push в `main` запрещены.
- Старый `dev` должен быть сохранён отдельной архивной веткой до синхронизации с `main`.
- Каждая задача выполняется в короткоживущей ветке `codex/<task-id>-<slug>` от актуального `dev`.
- Сабагенты, которые изменяют код, работают в отдельных git worktree и не редактируют одни и те же файлы.
- Итоговая интеграция выполняется последовательно в `dev`. В `main` создаётся один финальный PR после общего verification gate.
- Изменения `ExperimentSpec`, `ResultSpec`, RunRecord, общего pipeline, формата evidence bundle и настоящего файла `AGENTS.md` являются cross-cutting. Их интегрирует основной агент.

## Границы проекта

Обязательный объём до защиты:

- UCI Individual Household Electric Power Consumption;
- `Global_active_power`, почасовая частота, 12 000 часов, горизонты 1 и 24;
- каузальная предобработка и хронологический split;
- persistence, seasonal persistence и Ridge AR;
- ESN, Leaky ESN, LSM и Logistic на реальных данных;
- fair HPO, пять seed для стохастических моделей;
- MAE, RMSE, NRMSE_std, MASE и skill;
- p50/p95 latency, throughput, peak RSS, размер модели и состояния;
- dataset manifest, frozen/resolved specs, сырые RunRecord и агрегаты;
- воспроизводимый EDA, CI, demo и документация.

Не входят в обязательный объём:

- аппаратные измерения энергии и график quality-energy;
- добавление новых моделей;
- переработка сервисной архитектуры;
- промышленный Edge deployment;
- полноценная квантовая симуляция;
- расширение real-data матрицы за пределы утверждённых семи моделей.

## Инварианты данных и экспериментов

- Никакого случайного перемешивания временного ряда.
- Scaler обучается только на train.
- Заполнение пропусков не использует будущие значения.
- Восстановленные целевые точки исключаются из основных метрик.
- HPO использует только train/validation. Test запрещено использовать для выбора модели, гиперпараметров и ранней остановки.
- Все настраиваемые резервуары получают одинаковый HPO-бюджет.
- Frozen spec и фактически запущенный resolved spec сохраняются раздельно.
- Любая итоговая точка должна быть связана с commit SHA, seed, конфигурацией, датасетным manifest и аппаратным профилем.
- Энергия не оценивается через TDP, CPU time или паспортную мощность. Без аппаратного счётчика статус всегда `unavailable`.

## Правила изменения кода

- Сначала добавь тест, воспроизводящий дефект или новый контракт, затем минимальную реализацию.
- Не форматируй и не переписывай несвязанные файлы.
- Не меняй публичные схемы молча. Зафиксируй решение в `docs/agent/DECISIONS.md`.
- Не добавляй исходный UCI-датасет, credentials, `.env`, hostname, абсолютные локальные пути, кэши, БД или временные артефакты в Git.
- Не удаляй существующие тесты ради зелёного CI. Устаревший тест исправляется или явно переносится в integration suite.
- Не заявляй результат в README или презентации до появления проверяемого evidence bundle.

## Verification gate

Минимальная проверка задачи:

```bash
bash scripts/verify.sh quick
```

Перед интеграцией экспериментального блока:

```bash
bash scripts/verify.sh smoke
```

Перед финальным PR:

```bash
bash scripts/verify.sh release
```

Если этап ещё не реализован, соответствующий режим должен завершиться понятной ошибкой, а не молча пропустить обязательную проверку.

## Завершение задачи

Перед передачей результата:

1. Запусти проверки из Definition of Done.
2. Просмотри `git diff --check` и `git diff --stat`.
3. Заполни `docs/agent/HANDOFF_TEMPLATE.md` в сообщении основному агенту.
4. Обнови статус задачи в `BACKLOG.md`.
5. Добавь запись в `DECISIONS.md`, если принято новое устойчивое решение.
6. Укажи известные ограничения и проверки, которые не удалось выполнить.
